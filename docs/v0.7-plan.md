# M5GO Presence Platform v0.7 Plan

Status: Implementation complete; hardware acceptance in progress

v0.7 turns the current always-on presence display into a device that can explain
its own state, report and recover from common failures, and receive normal
firmware updates without a USB data connection. It deliberately preserves the
current presence and display behavior unless a requirement below says otherwise.

## Confirmed product decisions

- Short-press B remains the ordinary wake action.
- Long-press B opens an on-device diagnostics page.
- The normal dashboard header gains a compact device-health indicator.
- Every presence-state transition is recorded with its decision reason and the
  evidence needed to explain it later.
- The current `COOLDOWN` brightness behavior is unchanged:
  - `PRESENT` uses brightness 255.
  - entering `COOLDOWN` immediately uses brightness 60.
  - PIR or an allowed sound bridge may return directly to `PRESENT` and
    brightness 255.
  - expiry of `COOLDOWN` enters `IDLE` and brightness 0.
- v0.7 does not add a smooth fade, delay dimming until the end of cooldown, or
  otherwise suppress the existing `255 -> 60 -> 255` sequence.
- The Console remains directly usable from `192.168.0.0/24` without a user
  token. An application-level exact `/32` allowlist also admits the configured
  Mac through devb's existing Tailnet listener. Existing device API
  authentication remains unchanged.
- v0.7 does not add Caddy or change Tailscale, LAN addressing, or the existing
  explicit Uvicorn listeners.

## 1. Device health telemetry

The firmware must publish a bounded health snapshot at startup, whenever the
overall health level changes, and every 60 seconds while running. Health
reporting must never block sensor sampling or display rendering.

The latest health snapshot must include:

- firmware semantic version, Git commit/build ID, device ID, boot ID, uptime,
  boot count, and reset reason;
- Wi-Fi connection state, local IP, RSSI, reconnect count, and time-sync state;
- desired, stored, and currently applied presence-configuration revisions;
- age and result of the latest telemetry acknowledgement, configuration poll,
  room fetch, and weather fetch;
- main-loop and uploader-task heartbeat ages and task stack high-water marks;
- telemetry and feedback RAM queue depths, capacities, and drop counters;
- ordinary spool, feedback spool, and dead-letter counts, oldest backlog age,
  and LittleFS used/free bytes;
- current free heap, minimum free heap, and largest free block;
- PIR and microphone health/degraded flags; and
- current OTA/debug-session state when either feature is active.

No password, bearer token, signing secret, raw microphone audio, or other secret
may appear in health telemetry, logs, the diagnostics page, or the Console.

The device computes only its local health level:

- `healthy`: the complete expected data path is operating;
- `degraded`: the main presence function remains usable but a recoverable fault,
  stale feed, backlog, weak Wi-Fi, or sensor limitation exists;
- `action_required`: uploading, storage, OTA, or a required task is halted and
  operator action is needed; and
- `unknown`: local health has not been initialized yet.

The device cannot know whether the backend currently considers it offline. The
backend must retain the latest local health state and a bounded recent history,
then independently overlay `offline` when no telemetry or health report has
arrived within the existing server-observed online threshold. The Console must
show both the last reported local level and the server-derived connectivity
state instead of collapsing them into one value.

## 2. Dashboard health indicator

The existing dashboard header must show one small health indicator without
adding another page of ordinary dashboard data:

- green for `healthy`;
- yellow for `degraded`, including Wi-Fi disconnection or a stale backend
  acknowledgement;
- red for `action_required`; and
- grey while health is unknown or the device is still initializing.

The indicator must use the existing header-only redraw path. It must not cause a
full-screen refresh, visible flicker, or a change to the one-second Eastern-time
clock update.

## 3. Long-press B diagnostics page

- A short B press continues to wake the display and creates no human label.
- Holding B for at least 1.5 seconds opens diagnostics and keeps the screen
  awake while diagnostics are visible.
- The page shows the most useful local values even when devb is unreachable:
  device/build identity, IP/RSSI, uptime/reset reason, presence state and last
  transition reason, configuration revision, API/clock/feed freshness, queue and
  spool levels, heap/storage levels, sensor health, and OTA/debug status.
- The page must clearly show the difference between Wi-Fi failure, backend
  rejection, filesystem/backlog failure, sensor degradation, and stale dashboard
  sources.
- Short-press B exits diagnostics. After 60 seconds without input, diagnostics
  returns to the normal dashboard without changing the presence state. This
  timeout is suspended while an OTA window or upload is active.
- While diagnostics owns the buttons, A and C must not accidentally create
  `PRESENT` or `ABSENT` feedback labels.
- Secrets and raw core dumps are never displayed.

## 4. Explainable state-transition records

Every actual presence-state transition must remain an immediate critical record
and include or be joinable to:

- previous state, next state, transition reason, sequence, and uptime;
- PIR level and age of the latest PIR evidence;
- sound-active state and age of the latest accepted sound evidence;
- microphone envelope, learned noise floor, and active threshold;
- brightness before and after the transition;
- applied configuration revision; and
- firmware build ID.

The latest transition reason and its age must be available on the diagnostics
page and in the Console. Existing raw-audio privacy behavior remains unchanged:
only derived microphone measurements may be recorded.

Health-level changes, OTA phases, debug-session starts/stops, sensor degradation,
and recovery actions must also produce structured operational events. Repeated
steady state must be rate-limited rather than logged continuously as events.

## 5. Worker supervision and self-recovery

- LittleFS initialization failure must enter a bounded retry/degraded state; it
  must not permanently delete the uploader task.
- The main loop and network worker must expose independent heartbeats and use an
  appropriately configured watchdog. Network request timeouts must not trigger a
  false watchdog reset.
- Recoverable network/server failures must keep using bounded exponential
  backoff. Conditions requiring operator action must be explicit and visible.
- An authentication or endpoint failure may use a very low-frequency recovery
  probe. A configuration-revision integrity conflict must remain conservatively
  halted until resolved.
- Reset reason, repeated-reset count, and the most recent failure phase must
  survive reboot. Repeated early boot failures must enter a visible safe mode
  rather than an endless restart loop.

## 6. Sensor self-test and degraded modes

The startup calibration and periodic runtime checks must detect more than a
single legal ADC value:

- microphone rail-value ratio, variance, repeated-value ratio, clipping, and
  usable dynamic range;
- PIR implausibly long high/low periods and absence of expected edges; and
- task/sampling timing overruns that make sensor evidence unreliable.

A sensor fault must be reported locally and remotely. When safe, the device must
continue with a documented degraded mode, such as PIR-only operation, rather
than silently treating a failed microphone as valid data. Sensor and network
faults are soft OTA-validation failures unless the new application itself cannot
run its required tasks.

## 7. Offline backlog policy

- State transitions and human feedback retain priority over ordinary periodic
  samples in both RAM and flash.
- Flash capacity must be governed by reserved bytes/watermarks as well as file
  counts. Ordinary telemetry must not consume the space reserved for transitions,
  feedback, and crash/OTA metadata.
- As an outage grows, ordinary steady-state sampling may degrade from 1 second
  to coarser intervals while transitions and feedback remain immediate.
- Recovery must return to the configured normal interval automatically.
- Health data must expose the oldest backlog age, watermarks, and all discarded
  counts. Corrupt or unrecognized spool files must be quarantined without
  blocking later valid records.

## 8. Development OTA push

The first v0.7 installation still requires one USB flash because the currently
deployed firmware has no OTA entry point. After that bootstrap, ordinary
application builds can be pushed over the trusted LAN.

- Add a separate PlatformIO OTA upload environment using `espota`; keep the
  existing serial upload environment as the recovery path.
- The device must not run a permanently open development OTA listener.
- From the diagnostics page, holding A+C together for 3 seconds opens a visibly
  counted-down 120-second development OTA window. Because diagnostics owns the
  buttons, this gesture must not create ordinary A/C feedback actions.
- The screen shows hostname/IP, upload progress, verification result, and reboot
  status while the window is active.
- Development OTA uses a per-device secret and is restricted to the trusted LAN.
  It is a convenience path, not the production trust boundary.
- Interrupted, oversized, or corrupt uploads must leave the current application
  bootable.

## 9. Production signed OTA through devb

The operator experience is a Console release action, but the M5GO initiates the
firmware download. The ESP32 must not expose a permanent production upload port.

### Release artifact

Each release consists of an immutable manifest, `firmware.bin`, and the exact
matching `firmware.elf`. A v1 signature uses ECDSA P-256 over SHA-256 and stores
the signature as a fixed 64-byte `r || s` value. The signed bytes are a
versioned, length-prefixed binary record in network byte order rather than a
serialization of arbitrary JSON. The record must bind at least:

- hardware/model compatibility;
- firmware version and monotonic release counter;
- build/Git ID;
- image byte length and SHA-256 digest; and
- signing key ID and signature-format version.

The signing private key must not be stored on the M5GO or served by devb. devb
hosts only already signed release artifacts. Ordinary wireless downgrade is
rejected; intentional recovery remains possible over USB without burning an
irreversible eFuse anti-rollback policy in v0.7.

The firmware carries a small trust set containing the current and next public
keys. A manifest cannot replace that trust set; a new key becomes trusted only
through an application image signed by an already trusted key. A local packaging
tool creates and signs the immutable bundle, then imports it into devb. devb
must verify the bundle before storing it, and the Console may select only an
already imported, verified release. The private signing key remains in the
developer/CI secret store and is excluded from Git.

The development-OTA per-device secret is generated by the trusted USB
provisioning tool, stored in the device's atomic settings record and in an
operator secret store, and can be rotated only through USB or a physically
confirmed maintenance flow. It is separate from the production signing key.

### Desired-state and command transport

Console actions write desired state to devb; devb never opens a connection to
the ESP32. While connected, the device polls an authenticated device-control API
every 5 seconds. Poll failures use jittered exponential backoff up to 5 minutes,
and a successful poll restores the normal interval. The response contains the
desired release and at most one leased command.

Every command has a unique ID, creation time, expiry time, and payload. The
device durably records acceptance before a side effect and reports one of
`accepted`, `running`, `succeeded`, `failed`, `expired`, or `rejected`. Repeated
delivery of the same command ID must never repeat the side effect. A desired
release remains visible until the device reports the running, rejected,
failed, or rolled-back terminal result. Polling and acknowledgements must not
depend on a browser remaining open.

### Device update flow

1. Receive a desired-release notification from the authenticated device API.
2. Confirm model, version, release counter, and available inactive-slot size.
3. Stream the image into the inactive OTA partition without buffering the whole
   image in RAM.
4. Verify byte count, SHA-256, manifest signature, and final image validity.
5. Select the inactive slot and reboot only after every verification succeeds.
6. Keep the new image pending while local boot checks run.
7. Mark it valid only after the main loop, uploader worker, NVS/config storage,
   LittleFS, and display initialization have remained healthy for a 30-second
   validation window.
8. Allow the bootloader to return to the previous image after an early crash,
   watchdog reset, or failed hard validation.

Backend reachability, weather availability, Wi-Fi association, and a physically
missing optional sensor are not hard validation gates; a temporary outage must
not cause an otherwise healthy image to roll back. The Arduino framework's
default pre-`setup()` automatic image confirmation must be overridden so this
validation window is real.

### Console and reporting

The Console must show desired, running, previous, and last-known-good versions,
plus update phase, progress, last error, and rollback outcome. Release selection
requires an explicit review/confirmation step. Update status is idempotent across
retries and power loss.

OTA in v0.7 updates only the application partition. It must not wirelessly
rewrite the bootloader, partition table, NVS settings, LittleFS contents, or
stored telemetry/feedback.

### Runtime responsiveness during OTA

Flash erase/write can cause short unavoidable stalls, so v0.7 uses measured
limits instead of claiming that OTA can never block execution:

- OTA writes are streamed in bounded chunks from the Core 0 worker, erase the
  inactive slot incrementally, and yield between chunks. Production flash
  transactions are serialized between the Core 1 ADC sampling windows, while
  the independent main-loop-gap metric still measures every flash pause.
- Instrumentation records the maximum main-loop gap and invalid microphone
  windows during both production and development updates. The cross-core
  flash/sensor serialization guarantee applies only to production OTA; the
  framework-driven development path is still rejected if its measured gates
  fail.
- The main-loop gap must remain below 250 ms throughout an accepted update.
- A microphone window whose actual sampling duration differs from its nominal
  duration by more than 25% is marked invalid and cannot extend presence.
- Fewer than 1% of microphone windows may be invalid over a successful update.
- More than five consecutive invalid microphone windows or any main-loop gap of
  500 ms or longer aborts or safely pauses the update and reports a degraded
  health event.
- Rejectable production gates complete before the final exact boot-partition
  handoff. Firmware never tries to undo that handoff by re-selecting the
  running slot, because ESP-IDF would mark the known-good image `NEW` and break
  rollback semantics.
- A/B/C input remains responsive within 500 ms, and no critical transition or
  human-feedback record may be dropped because of OTA traffic.

## 10. Wireless operational debugging

### Structured live logs

- Add a fixed-capacity RAM log ring. Producers only enqueue; the network worker
  batches delivery to devb.
- Default remote logging sends bounded structured operational events, not the
  current 4 Hz sensor stream.
- A time-limited debug session may enable detailed sensor samples for at most 10
  minutes, after which it automatically returns to the normal level.
- Debug-log overflow is counted and reported. Debug logs are not written to
  LittleFS, so they cannot wear flash or crowd out durable telemetry.
- The Console may present the live stream, but a slow or disconnected browser
  must never backpressure the device.

### Restricted one-shot commands

Remote commands must carry a unique command ID, expiry time, requested action,
and the lease/acknowledgement semantics defined by the authenticated control
poll. The supported v0.7 actions are limited to:

- capture a current diagnostic snapshot;
- temporarily change the remote log level;
- request microphone recalibration;
- request an immediate telemetry retry;
- reboot the application; and
- open the development OTA window when the required local confirmation is also
  satisfied.

There is no arbitrary shell, arbitrary memory read/write, remote credential
replacement, or unrestricted command execution.

### Crash dump collection

- On startup, detect and validate an unacknowledged flash core dump.
- Upload the raw dump with reset reason, device/boot ID, exact firmware build ID,
  and checksum through an authenticated device endpoint.
- devb must retain the exact matching ELF and produce a symbolized report.
- Erase or mark the dump acknowledged only after the backend confirms durable
  receipt.
- A core dump may contain stack-resident credentials. Raw dumps are stored with
  restrictive permissions and are not exposed for download by the tokenless LAN
  Console; the Console shows the sanitized decoded summary.

True source-level breakpoints, register inspection, and single stepping over
Wi-Fi are outside v0.7. Those require a physical JTAG adapter and a separate
debug configuration.

## 11. Build and recovery requirements

- Firmware version, Git commit, and build ID have one generated source of truth.
- Every published binary retains its matching ELF, manifest, signature, and
  checksums.
- USB serial upload and provisioning remain supported and documented.
- A recovery runbook covers invalid Wi-Fi settings, a broken OTA client, two
  unusable application slots, and bootloader/partition changes.
- No OTA or debug path may erase the durable telemetry spool, feedback, or
  stored presence configuration as a side effect.

## 12. Required validation before v0.7 release

- Native tests cover manifest parsing, bounds, signature/hash rejection,
  release-counter rules, health classification, command expiry/idempotency, log
  ring overflow, and the extended transition evidence.
- Existing firmware, tool, backend, contract, lint, and formatting suites remain
  green.
- Backend schema changes use an explicit migration, preserve existing history,
  and follow the established pre-deployment backup/restore procedure. Health,
  command, release, and crash-report retention limits are documented and tested.
- Hardware tests prove serial recovery and at least:
  - successful OTA from slot A to B and back on a later release;
  - interrupted download leaves the running image unchanged;
  - wrong model, size, hash, signature, and downgrade are rejected;
  - a deliberately failed first boot rolls back to the last-known-good image;
  - temporary Wi-Fi/devb loss does not cause a false rollback;
  - development OTA is unreachable outside its physical time window;
  - a synthetic crash survives reboot, uploads once, and decodes against the
    exact ELF;
  - diagnostics remain usable with devb offline;
  - OTA, logs, and health uploads satisfy the quantified loop-gap, microphone,
    button-response, and critical-record limits above; and
  - the original `PRESENT=255`, `COOLDOWN=60`, `IDLE=0` brightness transitions
    remain unchanged, including an allowed `60 -> 255` return from cooldown.

## Explicitly outside v0.7

- changing the presence-state algorithm to a confidence/lease model;
- changing cooldown brightness timing or adding a smooth fade;
- automatic parameter tuning without reviewed human labels;
- sound-only wake, speech recognition, or raw-audio storage/upload;
- TMOS/mmWave integration or other new presence hardware;
- deep sleep or aggressive battery optimization;
- arbitrary remote shell or true Wi-Fi GDB;
- wireless bootloader, partition-table, NVS, or filesystem migration;
- public-internet exposure, Caddy, or Tailscale changes; and
- additional dashboard/weather pages or decorative animation work.
